### F1 - Chat webhook delivery bypasses its own DNS pin for a trailing-dot host (CONFIRMED, Medium)

`ChatDelivery::vetUrl()` normalises the host (lower case, trailing dot stripped) and `post()` pins the connection with `CURLOPT_RESOLVE` keyed on that normalised host, but `post()` passed the ORIGINAL URL to `curl_init()`. For `https://hooks.example.com./path` the vetted host (`hooks.example.com`) never matches the pin entry, so curl resolves the name itself. An administrator who can add a Slack/Teams destination can point a hostname they control at a public address for the vetting lookup and an internal or metadata address for curl's lookup (DNS rebinding). Reproduced locally: with `CURLOPT_RESOLVE=['pin.invalid:PORT:127.0.0.1']`, `http://pin.invalid:PORT/` connects and `http://pin.invalid.:PORT/` fails with "Could not resolve host", i.e. curl bypasses the pin. The same class was already fixed for the `send_webhook` automation action (SR-04, `pinnedUrl()`), and RivetCore's dispatcher uses it; `ChatDelivery::post()` (also reached from `SlackInteractive::respond()`) was missed.
Impact: server-side request forgery to internal services (POST with a fixed JSON body, response snippet stored and shown in delivery logs). Requires admin rights to configure a destination, hence Medium.
Fix: `curl_init(WebhookDispatcher::pinnedUrl($url, [host, port, ips]))`. Test: `tests/chat_delivery_pin.php`.

### F2 - Quote link can change the state of any quote (CONFIRMED, Medium)

`guest/guest_post.php` accepted `accept_quote` / `decline_quote` for any quote whose id and `url_key` matched, with no status or expiry check. The page only renders the buttons for Sent/Viewed quotes (and, by an operator-precedence slip, ignores expiry for Sent), so the restriction was UI-only. Anyone holding the emailed link could POST to turn an Invoiced or Declined quote back into Accepted (the agent side offers to invoice an Accepted quote, so this can bill twice), flip Accepted/Declined repeatedly (notifications, webhooks, `customAction('quote_accept')` hooks fire each time), or accept a quote after it expired and its prices lapsed.
Fix: the lookup now requires `quote_status IN ('Sent','Viewed')`, and accept also requires `quote_expire IS NULL OR >= CURDATE()`. Test: `tests/guest_quote_state_guard.php`.

### F3 - Negative payment amount accepted (CONFIRMED, Low)

`add_payment` rejected only `amount > balance`; `-500` passes and is inserted as a negative payment, re-opening a paid invoice or understating receipts. Needs `module_financial >= 2`, so it is an integrity/insider issue. Fix: refuse `amount < 0` (zero stays allowed so zero-total invoices can still be settled). Test: `tests/payment_negative_amount_guard.php`.

### F4 - Department restriction not applied when editing or deleting a payment (CONFIRMED, Medium)

`payments` has no client column. `edit_payment` called `getFieldById('payments', id, 'payment_client_id')`, which for an unknown column falls back to the row's own primary key, so `enforceClientAccess()` tested whether the user may access the department whose id equals the payment id. `delete_payment` read `$row['payment_client_id']` (always unset) so the department check always saw "no department" and passed. A non-admin restricted to some departments (rows in `user_client_permissions`) with Financial edit/delete rights could change or delete payments of departments they cannot see; delete also recomputes and rewrites the invoice status. This is a concrete call-site instance of the known `getFieldById` fallback behaviour (deferred); the fallback itself is untouched.
Fix: take `invoice_client_id` from the payment's invoice in both handlers. Test: `tests/payment_department_scope.php`. A scan of every literal `getFieldById(table, id, column)` call against `db.sql` found only one other missing column (`payment_providers.provider_name`, cosmetic, only the log text).

### F5 - Stripe payment can be recorded twice (HIGH CONFIDENCE, Medium) - not fixed

Five writers record `payments.payment_reference = 'Stripe - <pi>'`: `guest/payment_webhook.php`, `guest/guest_pay_invoice_stripe.php`, `cron/cron.php` (autopay), `client/post.php` and `agent/post/payment.php` (saved-card payments). Only the first two do an existence check, it is check-then-insert with no lock, and `payments` has no UNIQUE key on `payment_reference`. The browser redirect and Stripe's `payment_intent.succeeded` webhook normally arrive within the same second, and the three saved-card writers never check at all while the webhook fires for their PaymentIntents too (they carry `itflow_invoice_id` metadata). Result: duplicate payment row and duplicate gateway-fee expense; the invoice is still marked Paid, so the books are overstated rather than the customer overcharged.
Why not fixed tonight: the root-cause fix is a UNIQUE index (or a dedicated payment-intent column) plus `INSERT IGNORE`/duplicate handling in all five writers, which needs a migration (not allowed). A `GET_LOCK` shim in five financial code paths without DB tests was judged riskier than the bug.
Recommended: migration adding a unique key on a normalised provider reference; make every writer idempotent on it.

### F6 - Shared-file view limit is check-then-increment (POSSIBLE, Low)

`guest/guest_download_file.php` checks `item_views >= item_view_limit`, streams the file, then increments. Parallel requests can exceed a limit; the increment is also a read-modify-write. Fix: `UPDATE ... SET item_views = item_views + 1 WHERE item_id = ? AND (item_view_limit = 0 OR item_views < item_view_limit)` before sending the file.

### F7 - Unquoted Content-Disposition filename (POSSIBLE, Low)

`header('Content-Disposition: attachment; filename=' . $file_name)` with the stored name (tags stripped, SQL-escaped, not quoted). Spaces and `;` change the parsed filename parameters. `attachment` plus `nosniff` limits it to a cosmetic/parameter-confusion issue; newline injection is blocked by PHP. Use the quoted/`filename*` form used elsewhere in the codebase.

### F8 - Unbounded size on two unauthenticated-ish write paths (POSSIBLE, Low)

`guest_quote_upload_file` (anyone with a quote link) and portal `client_add_document` (`saveBase64Images`) write contact-supplied bytes with no size cap beyond PHP limits and, for the PDF upload, an extension-only type check (`checkFileUpload`). Storage exhaustion / mislabelled content. Content is served with `attachment` and `nosniff`. Add a size cap and a content sniff (as `api/v1/ticket_attachments.php` already does).

### F9 - False positive

`sha1(uniqid(mt_rand()))` for the OAuth `state` in the mailbox/mail settings handlers is only the `catch (Throwable)` fallback after `random_bytes()`; the normal path is CSPRNG. `generateReadablePassword()` uses `rand()/shuffle()` but has no callers.

## Disproved High/Critical candidates

- SSRF in the new webhook platform: `UrlPolicy` rejects loopback/private/link-local/metadata/mapped/NAT64/6to4/Teredo, requires every resolved address to pass, pins with `CURLOPT_RESOLVE`, disables redirects and proxies, and caps the body; only `ChatDelivery::post` leaked (F1).
- Unauthenticated installer download (`agent_installer.php`): token never read from the query string, generic 404, constant-time hash compare run even without a row, per-IP and per-selector DB rate limits, uses/expiry enforced, payload bounded, TLS required.
- Endpoint agent job authz: role and department checked on every call in `Authz`/`Actions`, free-form PowerShell needs a separate level, limited logins can only view, job cancel is scoped to the authorised device.
- MCP server: RS256 only, audience/scope/claims guard, identity bound to one active linked agent, read-only prepared queries with client scope.
- Passkey login: RP ID hash, origin, UP/UV, signature and counter verified; challenge single use.
- Post-login redirect (`last_visited`) is restricted to `/agent` and `/admin` paths appended to the configured host.
- CSRF scan of every action block in the three post handlers found no unprotected state change (all hits were nested conditions inside protected blocks, plus intentional GET exports/logout).
- Request-to-SQL sink scan found no unsanitised request value in a query string; no `unserialize`, `eval`, `include` of request data, or XXE-enabling libxml flags; no secrets or private keys in tracked files (one `ghp_`-shaped string is a Go test fixture).
